01The problem

Agents write code that moves money. Then they test it.

Payments, SMS, email, auth. Every integration needs something to talk to, and every option today costs you something.

Real keys
Real consequences. The agent can charge cards, text real people, burn credits and hit rate limits. One loop away from a bill.
Sandboxes
Accounts everywhere. A sign-up and keys for each provider, each set up differently. Many regional providers barely offer one.
Hand-written mocks
Lies that pass. Canned JSON that breaks the moment the code does something new, or passes against an API that behaves nothing like the real one.

02The twin

Not a mock. A twin.

A small working backend that acts like the provider. It remembers, it follows the rules, it sends the webhooks. Here is an agent building a checkout against one.

Remembers
Create it, then get it back. Customers, payments, messages and issues persist. Refunds change what is left to refund. Deleted things are gone.
Behaves
Real shapes, real lifecycles. Provider-style IDs, pagination and errors. Flows like queued → sent → delivered. Webhooks are signed the way the provider signs them, so your verification code runs unchanged.
Breaks on purpose
Failure, on demand. Declined cards, 3-D Secure, bounced email, unreachable phones. Force any of them from the dashboard or from your agent.

06Chaos

Find the failure before your users do.

Turn on chaos and the twin misbehaves like a provider on a bad day. It is seeded, so a failure your agent finds can be replayed exactly.

Chaos modes
timeoutRequests hang until your client gives up.
5xx500, 502 and 503 in the provider's error shape.
429Rate limits with Retry-After.
slowResponses take one to four seconds.
dup-webhooksThe same event, delivered twice.
out-of-orderEvents arrive shuffled.
$ npx mockanything stripe --chaos --seed 42

07Safety

Nothing real leaves your machine.

Local only
Listens on localhost. Webhooks go to localhost unless you allow a host.
No live keys
Live keys are refused. Any placeholder works.
No real cards
Real-looking card numbers are refused. Use documented test values.
Plain test pages
Checkout and 3-D Secure pages are unbranded and say they are not real.
No telemetry
Mock Anything does not phone home.

A twin is only as good as its facts. Packs cover each API's main flow, not every endpoint, and inferred twins make guesses you can see and override. Build fast against a twin; run final checks against the provider's sandbox. A fidelity report that compares a twin with the real sandbox is on the way.

08Questions

Frequently asked questions

Is Mock Anything affiliated with Stripe, Twilio or the other providers?

No. Mock Anything is an independent, free, non-commercial project. Provider names are used only to say which API a twin is compatible with. Twins are built from public API facts, not from any provider's code or documentation text.

Do I need an account or API key?

No. Any placeholder key works, for example sk_test_mockanything. Live keys are refused.

Does anything I send leave my machine?

No. The twin runs locally and answers from memory. The only outbound traffic is the webhooks you point at your own app, and fetching an API description when you ask for one by name or URL.

Which APIs work?

Anything with an OpenAPI or Swagger description, the 2,529 APIs listed by name in the public APIs.guru directory, the built-in packs, and APIs your agent describes from their documentation.

Can I use it in CI?

Yes. Start a twin before your tests and point your SDK's base URL at it. Use --seed to make chaos runs repeatable.

How do I add a provider?

Packs are plain YAML. The contributing guide in the repository explains the rules: facts only, no branding, and a test with the official SDK.
